# Conversation lifecycle

## What it is

Each cold app launch starts a fresh chat while earlier conversations remain available in Chats. All conversational replies, including explanations of tool outcomes, are generated by the local model.

## How it works

The archive adds optional conversation identity/history fields so existing records migrate without a destructive reset. Before replacing a nonempty conversation, the store upserts it into history by identity. Restoring a chat removes its history entry until it is archived again, avoiding duplicates.

The model selects from the complete tool catalog or ordinary `reply`. Topics are hints, not commands. Source parsers validate model-selected actions and changes open existing review screens. Tool data is saved with an explicit completion/confirmation status; a separate local generation explains that actual result. Failure produces a retry control, never a fixed conversational fallback. Cancelled generations cannot append a late response to a new chat. Emergency wording triggers a separate UI alert while conversation still uses the model.

The chat dock is smaller and lower than the other tabs with a spring transition. All touch targets remain at least 44 points; Reduce Motion disables movement.

## How to change it

Edit prompt contracts in `HarbourCore/ToolPlanner.swift`, inference in `ModelManager`, and orchestration in `ChatView`. Keep machine tool status distinct from model-authored prose. Update persistence tests and the text evaluation suite when changing routing, context, or result narration. The archive format must remain backward compatible.

## Configuration and dependencies

Uses AppStore's protected JSON archive, HarbourCore, HarbourRuntime, and the selected downloaded GGUF. Context currently retains six recent messages, each limited to 500 characters, plus a limited record snapshot; this is not unlimited conversation memory. Chat effort controls routing/reply token budgets, not visit-summary extraction. No cloud LLM service is configured.
