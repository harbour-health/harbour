# Interface

## What it is

A native SwiftUI health companion with Today, Chat, Records, and Visits destinations. The summary hierarchy and floating navigation take inspiration from the supplied Wealthsimple reference, with original Harbour artwork and familiar iOS controls.

## How it works

Today opens first. Its reading summary groups the latest value, unit, recorded date, and sample count in one surface. A chart appears only when at least two saved readings of the same kind exist, using the most recent 30 samples in date order. Blood pressure plots systolic pressure and labels that series. No health score, invented sample, or clinical interpretation is added.

[Navigation and actions](navigation-and-actions.md) defines the shared toolbar positions, control sizes, and primary/secondary button styles. Settings is at the upper right of all four main destinations; creation actions occupy the opposite side when present. Nested screens retain native Back and their own task actions. Today shows additional reading types separately, with no repeated row for the summary's metric.

Medicines and Symptoms use equal-width, equal-height shortcuts (210 points at normal text sizes). The reading summary and both shortcuts share a 14-point vertical/horizontal gap. Their original illustrations extend beyond the bottom/right edges and are clipped; a contrasting circular arrow sits at the bottom left. Artwork is an overlay so its fixed drawing width cannot force the tiles or dashboard beyond the phone's margins. The medicine shortcut opens its record list, while Symptoms opens capture. Secondary actions and recent symptoms remain open rows. Rounded bold system type is reserved for shortcut titles, metric values, and PIN headings; ordinary labels use the system typeface.

A detached capsule dock contains only Today, Chat, Records, and Visits icons. Accessible names and selected traits remain. Native labelled tabs are hidden within each navigation stack, while `TabView` preserves destination state. The dock is an overlay on `TabView`, with a pale grey capsule in Light and a charcoal capsule in Dark. Its background occupies only the capsule; surrounding content remains visible and scrolls behind it. The `floatingDockClearance` environment value adds 86 points of scroll-content margin to Today and record lists, allowing their last controls to scroll above the dock. Chat reserves the same space below its composer so input controls remain usable. This spacing is applied inside each destination because a safe-area inset on the outer tab container did not reliably resize its child controllers. The dock remains mounted while the keyboard is shown, with zero opacity, disabled hit testing and hidden accessibility; clearance becomes zero. Keeping the native view mounted avoids rebuilding its controls during keyboard transitions.

A pure white light canvas and neutral charcoal dark canvas replace the earlier cream palette. Reading summaries and the composer use a subtle neutral surface to separate controls without tinting the whole screen. Semantic ink, secondary text, divider, and accent colours have separate light and dark values. Settings → Appearance offers System (default), Light, and Dark. The choice persists across launches and applies to navigation, chat, and sheets. System leaves SwiftUI's preferred colour scheme unset so subsequent phone appearance changes still apply.

Chat has an original animated conversation illustration, three open starter rows, and a high-contrast composer. Its text area reserves two lines and at least 82 points in portrait (54 in compact-height layouts), with controls beneath rather than squeezed alongside the draft. Model name, lighter effort label, and chevron remain immediately left of the microphone. A selected topic appears on its own line. Selecting a starter or topic preserves the draft, executes no action, and adds only an optional model prompt hint. The navigation title starts with “New chat” and uses [local title generation](chat-titles.md) after the first message.

Medicine, reading, and interaction tool results have a single illustrated surface per result; reminders and history use compact open rows. Medicines, readings, and cited interaction findings render as structured content inside that surface, without nested cards. Unsupported interaction pairs remain explicitly unassessed. Record mutations still require their existing confirmation sheets. App-owned sheets use [floating drawers](floating-drawers.md) with compact task-specific heights and four rounded corners; longer content remains scrollable. The waiting mark spins and new messages appear with a short transition; Reduce Motion disables these effects and the finite illustration arrival. Buttons have restrained press feedback.

Records uses an Apple Health-inspired category browser instead of segmented tabs. Three full-width rows provide large category labels, coloured glyphs, saved counts, and chevrons. Each opens a dedicated list with its own large title and Add record action; the native back button returns to the browser. Flat lists retain native swipe deletion. Today’s medicine shortcut sets the optional category destination before selecting Records, so it still opens Medicines directly. The navigation binding resets when the user goes back and is not stored with health records. Empty states retain the list toolbar as the single Add action. Input forms retain native grouping for familiar pickers, keyboard handling, and confirmation controls. Emergency options use rounded, lightly coloured selection buttons. There are no marketing sections or prototype disclaimers in navigation; clinical instructions and provenance remain visible where needed.

Visits follows the [Google Recorder](https://support.google.com/pixelphone/answer/16267367?hl=en) pattern with one large recording control, timer, waveform, and separate finish action. Its history uses open rows; a single illustrated recording entry point sits above them. Saved visit details separate summary and editable transcript, with source quotes and a deliberate medicine review step. See [Doctor visits](doctor-visits.md) for the recording lifecycle.

The empty chat uses a 204 × 160 point illustration and a compact top inset. Its layout reserves room for all three starter actions above the composer at the default text size; smaller viewports can scroll. `HarbourStableMainScreensTests` defines checks for the last starter above the composer and all four dock targets in both appearances. The English and Canadian French native flows verify reachability and starter placement. Screenshot review is a separate gate: a hittable accessibility target does not establish that its icon rendered.

The floating dock uses `house` for Today, `bubble.left.and.bubble.right` for Chat, `heart.text.clipboard` for Records, and `person.2` for Visits. Inactive symbols are dim outlines; the active symbol uses its `.fill` variant in near-black for Light or white for Dark. All use a regular-weight 22-point font. The opaque capsule is 278 × 62 points, enclosing four 62.5 × 54 point cells with 14-point horizontal and 4-point vertical padding. A single 83 × 54 point selected marker moves behind those cells. At the first and last positions its outer edge is inset 3.75 points from the capsule; it advances 62.5 points per destination. The marker moves with a 0.22-second UIKit ease-in/ease-out animation and moves immediately when Reduce Motion is enabled.

`DockView` resolves adaptive neutral colors against SwiftUI’s current color scheme on each update, including an in-app appearance override. Its transparent UIKit buttons handle actions and accessibility; a separate view synchronously renders tinted SF Symbols into an image layer above the moving selection marker whenever its bounds or icons change. This avoids intermittent missing button images during tab and keyboard transitions. The symbols represent the home screen, a conversation, medical records, and a meeting with a doctor. The Visits icon represents the whole destination, which includes notes and summaries as well as recording. Active recording appears as a small coral dot and a localized accessibility value, preserving the selected icon’s appearance. Localized accessibility labels and the large-content viewer remain available. Update the hidden native TabView labels alongside the custom dock when changing symbols; retain the stable `nav-today`, `nav-chat`, `nav-records` and `nav-visits` identifiers.

## How to change it

`HarbourApp.swift` owns navigation, Today, shared rows, and the mark. `Dashboard.swift` owns the icon dock and saved-reading summary/chart. `ChatView.swift` owns the composer, optional topics, transcript, and structured tool-result presentation. `RecordsView.swift` owns the category browser, `RecordList` destinations, and editors. `RootView.recordCategory` is an optional integer navigation destination (0 symptoms, 1 medicines, 2 readings); keep those indices aligned with the browser and Today shortcut. `Appearance.swift` contains semantic colours, the appearance setting, and press feedback. See [Artwork](artwork.md) for illustration changes and [App lock](app-lock.md) for protected entry.

Keep whole-row hit areas with `contentShape`, use system text styles for labels, and preserve at least 44-point control targets. Today stacks equal-height 320-point shortcuts vertically at accessibility text sizes. Test narrow screens and large text before changing composer spacing. Derive charts only from actual records and identify partial metrics, such as systolic-only blood pressure. Do not add a success badge when an interaction has not been assessed. Presentation changes must not bypass the deterministic rules or original-message tool validation.

## Configuration

The Light dock uses `#F1F1F1` for its capsule, white for its selection, `#181818` for the selected symbol, and `#969696` for inactive outlines. Dark retains the `#232323` capsule, `#0D0D0D` selection, white active symbol, and `#5B5B5B` inactive outlines. Adaptive dock colors live in `Appearance.swift`; `Dashboard.swift` resolves them explicitly against the current color scheme before rendering its image layer and border. Dock dimensions, selection offset and animation duration also live in `Dashboard.swift`. Keep the 278 × 62 point capsule, 62.5 × 54 point cells, 83 × 54 point marker and its 3.75-point edge inset coordinated when changing geometry.

`@AppStorage("appearance")` stores `AppearanceChoice.rawValue`; invalid values fall back to System. `Palette` uses adaptive UIKit colours resolved against the active appearance. `accessibilityReduceMotion` controls optional animation. Illustration frames and dashboard spacing are local SwiftUI constants. `RootView` sets `floatingDockClearance`; every new scrollable destination beneath the dock must consume it as a bottom scroll-content margin, while fixed bottom controls reserve that amount in their own layout. Keep backgrounds and hit regions confined to the capsule.

The app icon is original Harbour geometry, generated by `scripts/generate-icon.swift`. The effort control wraps `UISlider` with a 28-point rounded track and matching thumb, retains native dragging/accessibility, and snaps to three values. Its 48-point view frame keeps the hit area larger than the artwork. New top-level Swift source files require `python3 scripts/generate-project.py` to refresh the checked-in Xcode project. iPad, VoiceOver, and largest-accessibility-text acceptance remain device testing tasks.

## Dependencies

SwiftUI, Swift Charts, UIKit dynamic colours and keyboard notifications, SF Symbols, native tab state, and the original vector [artwork](artwork.md). No remote design assets or UI libraries are required.

Display text and accessibility labels use the bundled [localization](localization.md) resources. Longer French text changes wrapping but does not change the dock's stable navigation IDs or fixed geometry.

The category browser follows the browse-then-open pattern in [Apple Health](https://support.apple.com/en-ie/guide/iphone/iphe3d379c32/ios). The chat composer uses the supplied ChatGPT reference: a multiline draft above a separate control row. These are navigation/layout references, not copied artwork or third-party components.
