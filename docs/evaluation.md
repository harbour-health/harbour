## What it is

Reproducible native checks for the fixed health harness, validated tool calls, saved records, SwiftUI flows, and real on-device-runtime inference. This is an engineering feasibility suite; it does not establish clinical benefit or complete symptom/interaction coverage.

## How it works

Earlier snapshots recorded 87 Core methods and seventeen Runtime regressions on this branch, and 106 Core/eighteen Runtime tests on main. Intermediate development counts also belong only to their producing snapshots; the merged counts remain pending a fresh test run. Coverage includes care data, import, notification plans, voice turns, bounded French input, native tool/title/visit grammar initialization, and input rejection. The original four Runtime checks cover complete outer JSON, nested arguments, string braces, escapes, and incomplete output. A historical Core method also evaluated 29 named clinical fixtures, covering emergency checklist items, affirmative/negated phrases, unknown and duplicate ingredients, sourced pairs, combination ingredients, numeric extraction, invalid measurements, prompt-token escaping, aliases, and rejection of invented actions and empty replies. Further tests cover original-text anchoring, pair symmetry, ambiguous medicine requests, Codable round trips, and confirmed-fact appointment notes.

Native UI tests cover manual symptom/reading entry and persistence across relaunch; topic hints preserving the draft; model selection/effort; real Qwen chat for a sourced interaction, heart rate, and symptom review; and medicine confirmation/export. The model test uses the actual download and native runtime, not a mock. UIKit exposes SwiftUI links differently from a web link: test them by accessibility identifier rather than assuming the `Link` query role.

The in-app Evaluation screen runs the fixed checks, thirty-one fictional routing prompts, and nine transcript extraction cases at one or all three effort settings for the selected model. Each run exports the expected/observed tool, raw output, pass/fail, model, effort, elapsed time, OS version, thermal state, and device memory. Conversational fixtures generate an ordinary-text reply after selecting `reply`; reports preserve both the routing JSON and generated prose. Timing includes a download and model load if required for the first case; later cases reuse the loaded model. Device memory is total physical memory, not peak application memory. Failure is recorded rather than discarded.

## How to change it

Raw model output is retained even when parsing or original-message validation rejects it. This distinguishes a routing failure from an accepted action; rejected calls do not modify records.

Add cases in `HarbourCore/Evaluation.swift` and targeted invariants in `HarbourCoreTests.swift`. New clinical rules need independent source review and labelled reference cases; agreement with the implementation itself is not enough. Keep model prompts fictional and repeat the same fixtures across models, effort settings, and devices. Add model aliases only for known equivalent tools and retain original-message validation.
